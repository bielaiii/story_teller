# 架构审查第 3 项：小修改的保存成本

第一阶段修复日期：2026-09-10；第二阶段完成日期：2026-09-15。对照版本：`bef797c`。所有测量和持久化验收均使用临时数据库，没有修改实际小说数据。

## 第一阶段：事务审计与后台调度（历史记录）

1. 保存仍在一个 SQLite 事务里完成正文修改、版本推进、七天撤销记录和待导出版本登记。
2. 审计通过当前连接的临时触发器捕获每个受影响行的第一次修改前状态，事务结束前只按主键读取这些行的最终状态。未触及的正文、附件和回收站内容不再全量序列化。保存点回滚会同时回滚审计记录；级联删除、复合主键、主键变更和替换写入仍可正确比较并撤销。
3. Web 保存提交后立即返回已落库的数据和 `export.status=pending`。后台通常等待 0.5 秒合并连续保存；持续保存最多推迟启动 5 秒（已有导出运行时等待该任务结束）。导出期间发生新保存会安排后续任务，已被前一次导出覆盖的迟到请求会跳过。
4. 所有导出读取共享一个 SQLite 只读事务，生成期间允许正文继续写入。进程内各导出入口按项目串行发布；旧版本完成不会把较新的待导出版本标成完成。
5. 界面独立轮询导出状态，保留编辑器、未保存草稿和页面状态。导出失败明确显示“正文已保存，导出失败”；再次保存（包括无正文变化的请求）会重试。正常关闭服务会完成已接收的导出；异常退出留下的 `pending/failed` 由启动准备流程修复。
6. CLI 和显式导出仍同步生成文件；静态只读模式和不具备新能力的旧服务不启动状态轮询。

临时审计表和触发器只存在于本次连接，不修改持久化 Schema。全量 `_snapshot` 仅保留给显式合并规划，普通保存不调用它。`AGENTS.md` 已同步新的 Web 保存/导出约定。

## 第一阶段测量（不包含后台导出）

在同一机器上，分别复制演示数据库，增加如下数据；每组修改同一剧情标题 3 次。下表是带 `tracemalloc` 的中位耗时，内存是 3 次测量中的最大 Python 分配峰值。

保存处理链路包括事务、返回增量构建和导出提交；旧版等待完整导出，新版提交后台任务。测量不含浏览器、HTTP 传输和 RAG 索引。为隔离请求分配，测量时将后台延迟设为 60 秒，测量后关闭调度器并等待导出完成。生产延迟为 0.5 秒。

| 增加的数据 | 旧事务 / 新事务 ms | 旧保存链路 / 新保存链路 ms | 旧链路 / 新链路 Python 峰值 MiB |
| --- | ---: | ---: | ---: |
| 无，演示库 | 28.39 / 8.69 | 199.52 / 13.64 | 0.75 / 0.12 |
| 500 条正文，每条 8 KiB | 133.16 / 9.89 | 2074.23 / 17.61 | 29.59 / 0.12 |
| 32 MiB 附件 | 378.69 / 8.89 | 812.90 / 14.00 | 256.56 / 0.12 |
| 500 条回收站正文，每条 8 KiB | 133.61 / 9.78 | 373.82 / 16.48 | 25.21 / 0.12 |
| 500 条回收站正文 + 32 MiB 附件 | 491.59 / 8.96 | 996.54 / 14.64 | 281.21 / 0.12 |

复现命令（在 `story_teller/` 中）：

```sh
./scripts/python.sh scripts/benchmark_mutation_cost.py --baseline bef797c --repeats 3
```

这些结果说明未修改数据不再进入普通保存的全量审计和同步导出。它们不是实际小说的耗时承诺，也不是整个进程内存测量。完整后台导出的时间和峰值内存仍随数据量增长；普通读写仍执行已有完整性检查，不能据此声称保存成本严格为常量。本次未尝试分块流式导出或修改完整性校验策略。

## 第一阶段验证范围

- 行级审计与原全量快照逐行对照，覆盖多次修改、保存点回滚、替换写入、主键变更、级联删除、二进制附件撤销、语义无变化和事务异常。
- 用禁止二进制进入编码函数和禁止调用全量快照的测试，确认小修改不会处理未触及的 4 MB 附件。
- 连续保存合并一次导出；导出中继续保存产生后续任务；迟到请求不重复生成已发布版本；正常关闭排空任务；渲染故障保留正文并可重试；启动修复 `pending/failed`。

## 第二阶段：只提交变化字段，增量生成导出

第一阶段只把全量导出移到后台，仍会重复处理整套数据，因此不能视为第 3 项已经完整解决。本阶段补齐该部分。

- 剧情、人物、条目、碎片和关系编辑器对照真实编辑基线，只提交变化字段并保留版本校验。修改标题不再携带正文；只修改正文不再提交章节编号、触发章节重排。清空字段及关联字段组合仍能正确保存。
- 正文继续按单篇完整文本保存，这是当前编辑粒度；没有引入按行补丁、协同编辑协议或字符级历史。审计记录只涉及受影响行。
- 普通后台导出读取上次版本之后的变化，只读取受影响实体的详情，重建其 Markdown；名称、父子关系、章节和时间线变化会更新依赖项。未变文件保留 inode 与修改时间，改名和删除清理旧路径。
- 静态快照和完整恢复数据采用不可变基底加增量文件。普通保存不再遍历未变正文、附件或历史 before/after 数据。元数据摘要和操作目录仍随项目规模增长，因此不声称成本为常量。
- 导出格式版本升到 6，数据库 Schema 不变。`project.snapshot.json` 和 `recovery.snapshot.json` 在普通保存后可能是 `story-teller-export-journal` v1 清单，依赖同目录的 `export-data/`。静态读取器、恢复导入器、AI 导出说明均支持此格式。恢复历史与静态内容使用不同文件，静态打包只输出还原后的完整阅读快照。
- 每个基底最多附加 64 个增量，下一次导出整理完整基底；首次生成、缓存缺失或变化历史过期也重新生成。显式导出和 CLI 保持完整输出，静态打包脚本将增量还原成可独立读取的快照。手工迁移增量恢复包必须连同 `export-data/` 一起复制。
- 保留统一只读事务、跨进程锁、版本单调性和失败回滚。发布先安装不可变数据，再替换清单，最后更新索引；失败可重试。文件集逐文件发布的外部读取边界仍见第 2 项记录。

## 第二阶段验收

新增后端测试逐次比较增量还原与完整导出的内容，覆盖修改、改名、删除、撤销、二进制恢复、章节和时间线结构、父子碎片、缺失文件修复、历史过期、定期整理、发布失败与重试、损坏数据拒绝和静态打包。测试禁止普通增量调用全项目快照、读取无关实体详情或生成完整恢复快照。

浏览器在隔离临时库实际点击保存，并检查请求字段、API 回读、Markdown 内容及无关文件 inode/修改时间；静态浏览器分别验证完整与增量快照。所有持久化验收均未修改实际小说数据。
